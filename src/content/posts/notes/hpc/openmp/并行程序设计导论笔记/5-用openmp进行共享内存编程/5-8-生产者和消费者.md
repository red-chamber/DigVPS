在 OpenMP 的共享内存中，多个线程像“互发短信”一样传递消息，如何避免消息队列被同时修改而出错？

每个线程都有自己的“收件箱”——消息队列。如果线程 0 要给线程 2 发消息，它不是直接把消息交给线程 2，而是把消息放进线程 2 的消息队列，线程 2 之后再从自己的消息队列中取出消息并处理。这是一种“多个发送者、一个接收者”的队列模型。

程序中，每个线程大致执行：
```c
for (sent_msgs = 0; sent_msgs < send_max; sent_msgs++) {
    Send_msg();      // 随机给某个线程发送一条消息
    Try_receive();   // 顺便看看自己的队列有没有消息。如果队列容量比较小，这样可以避免队列溢出（称为交替接收）
}

while (!Done()) {
    Try_receive();   // 发完后继续接收，直到所有线程都结束
}
```
这样做的原因是：一个线程即使已经发完自己的消息，其他线程仍可能继续向它发送消息。它不能立即退出，否则别人发给它的消息可能永远无人处理。

## `critical` 指令

多个线程可能同时给同一个目标线程发消息。它们都会试图修改某线程消息队列的“尾指针”。若没有保护，可能发生：
```text
线程 0：认为队尾是 A
线程 1：也认为队尾是 A

线程 0：把消息 X 接到 A 后面
线程 1：把消息 Y 也接到 A 后面

结果：X 或 Y 其中一条消息可能丢失
```

所以入队操作必须放在临界区：
```c
#pragma omp critical
Enqueue(...);
```
同一时刻只允许一个线程修改队列结构。

#### 接收消息有时不需要锁

接收消息时，只有一个线程会从某个队列取消息，一个线程的消息队列，可以由多个线程入队，但只能由它本身出队。

队列中消息数量可以用两个计数器表示：
- enqueued：已经入队的消息总数
- dequeued：已经出队的消息总数
可知：`queue_size` = `enqueued` - `dequeued`；

接收函数的伪代码是：
```c
queue_size = enqueued - dequeued;

if (queue_size == 0) { // 队列为空，没有消息，直接返回
    return;
} else if (queue_size == 1) { // 队列中只有 1 条消息，入队和出队可能同时碰到同一个节点，需要 critical 保护
    #pragma omp critical
    Dequeue(queue, &src, &msg);
} else {  // 队列中至少有 2 条消息，发送线程和接收线程分别操作队尾和队头，互不干扰，不必加锁
    Dequeue(queue, &src, &msg);
}

Print_message(src, msg);
```

`queue_size` 的值偶尔不够新，未必导致错误。例如实际已有一条消息，但线程读取到 `queue_size == 0`，它只是暂时不接收，稍后再次调用 `Try_receive()` 时还会处理那条消息。这会造成一点延迟，但不会丢消息。反过来，实际有两条消息却误以为只有一条，线程会多执行一次不必要的 `critical`，性能略差，但结果仍正确。

#### 终止检测

如何实现 Done 函数（检测每个线程是否发送完了信息）？首先，我们给出一个“直接”的实现，但它隐藏着问题：
```c
queue_size = enqueued - dequeued;
if (queue_size == 0) return TRUE:
else return FALSE:
```
如果线程 u 执行这段代码，那么很有可能有些线程，如线程 v，在线程 u 计算出 queue_size =0 后向线程 u 发送一条消息。当然，线程 u 在得出 queue_size = 0 后将终止，那么线程 v 发送给它的消息就**永远不会被接收到**。解决办法很简单，加一个 `done_sending` 计数器，记录已经把信息全部发送完成的线程数，与总线程数比对即可。

之前我们见过一些 OpenMP 指令在结束时提供隐式路障，即任何一个线程都必须等到组中所有的线程完成了某个程序块后才可以接着执行后续代码。然而，在这个例子中，我们处于 parallel 块的中间，所以我们不能依赖于 OpenMP 提供的隐式路障—我们应当使用显式的路障：
```c
# pragma omp barrier
```
当线程遇到路障时，它将被阻塞，直到组中所有的线程都到达了这个路障。当组中所有的线程都到达了这个路障时，这些线程就可以接着往下执行。

## `atomic` 指令

`#pragma omp atomic` 用来保护一种很常见、很小的共享操作：
**多个线程对同一个变量做加一、加法、减法等更新。**

例如每个线程全部发送完消息后，要执行 `done_sending++`，假设当前 `done_sending = 5`，线程 0 和线程 1 同时执行 `done_sending++`。可以写：
```c
#pragma omp atomic
done_sending++;
```
意思是：
> 对 `done_sending` 的这次读、修改、写回，必须作为一个整体完成；其他线程不能插进来。

效果类似：
```text
线程 0：5 → 6
线程 1：6 → 7
```

#### `atomic` 和 `critical` 的区别

这两种都能防止竞争条件，但适用范围不同。`critical` 像一间只能容纳一个线程的房间，里面可以放多行任意代码：
```c
#pragma omp critical
{
    x++;
    y += x;
    printf("%d\n", y);
}
```

而 `atomic` 只能保护单个变量的简单更新：
```c
#pragma omp atomic
x++;

#pragma omp atomic
x += value;
```

`critical`：适合多行或复杂共享操作，通用，但开销通常较大
`atomic`：适合单个变量的简单读-改-写，限制多，但通常更轻量、更快

`atomic` 可用的运算符包括：
```text
+  -  *  /  &  ^  |  <<  >>
```

并且，它只保护 `OpenMP` 识别出的主变量：
```c
#pragma omp atomic
x += y++;
```
这里 `x` 的更新受到保护，但 `y++` 不受保护。

#### 为什么 `atomic` 往往更快？

`x++` 表面上只有一行，但底层其实是三步：
```text
读取 x
→ x 加一
→ 写回 x
```
这叫“读—修改—写”（load-modify-store）。现代 CPU 通常有专门的硬件原子指令，能够高效完成这类操作。

## 临界区和锁

`critical`、`atomic` 和“锁（lock）”都能实现互斥，但它们适合保护的对象不同。选错方式会让程序变慢，甚至死锁。

#### 1。全部用 `critical` 可能不能达到最好效果 

消息传递程序中，有三类需要保护的操作：
```c
done_sending++;                 // 所有线程共同更新一个计数器
Enqueue(q_p, my_rank, msg);     // 往某个消息队列放消息
Dequeue(q_p, &src, &msg);       // 从某个消息队列取消息
```
如果都写成 `critical`（未指定变量名），`OpenMP` 会把它们看成同一把“大锁”。结果是，即使两个线程在操作完全不同的队列，也不能同时进行。这样没有必要，会降低并发性。`done_sending++` 只是一个简单加一，适合 `atomic`，它不需要和队列操作互斥。

#### 2。为每个队列指定 `critical` 也不是最佳实践

可以给临界区命名：
```c
#pragma omp critical(queue_a)
{
    /* 操作队列 A */
}

#pragma omp critical(queue_b)
{
    /* 操作队列 B */
}
```
不同名字对应不同的互斥区域，所以可以并行执行。但消息队列的数量和目标队列是在运行时决定的，你无法方便地根据运行时的 `dest` 动态写：
```c
#pragma omp critical(queue_dest)  // 这不是合法的动态命名方式
```
因此，命名 `critical` 不适合“数组中每个队列各有一把锁”的需求。

#### 3。把锁绑定到数据，而不是绑定到某段代码

更合理的设计是：每个消息队列自带一把锁。
```text
消息队列 0  ── 锁 0
消息队列 1  ── 锁 1
消息队列 2  ── 锁 2
```

概念上，队列结构可写成：
```c
typedef struct {
    /* 队列的头、尾、计数器等数据 */
    omp_lock_t lock;
} message_queue_t;
```

发送消息时，锁住目标队列：
```c
message_queue_t* q_p = &msg_queues[dest];

omp_set_lock(&q_p->lock);
Enqueue(q_p, my_rank, msg);
omp_unset_lock(&q_p->lock);
```

接收消息时，锁住自己的队列：
```c
message_queue_t* q_p = &msg_queues[my_rank];

omp_set_lock(&q_p->lock);
Dequeue(q_p, &src, &msg);
omp_unset_lock(&q_p->lock);
```

如果两个线程都要访问队列 1，它们会竞争同一把锁，保证队列不会被同时破坏。这就是锁最适合的场景：
> 要保护的是某个具体数据对象，而不是某个固定的代码位置。

#### 4。简单锁的基本用法

```c
omp_lock_t lock;
```

常用函数：
```c
omp_init_lock(&lock);     // 初始化锁
omp_set_lock(&lock);      // 加锁；拿不到会等待
omp_unset_lock(&lock);    // 解锁
omp_destroy_lock(&lock);  // 销毁锁
```

典型生命周期：
```text
初始化锁
    ↓
多个线程反复加锁 → 操作共享数据 → 解锁
    ↓
所有线程不再使用锁
    ↓
销毁锁
```

简单锁有一个限制：同一个线程拿到同一把简单锁后，在解锁前不能再次获取它。否则线程会等待自己释放锁，造成死锁。
OpenMP 也有嵌套锁 `omp_nest_lock_t`，允许同一线程重复获得同一把锁；不过大多数初学阶段，更好的习惯是避免这种嵌套设计。

#### 5。`atomic`、`critical`、锁 三者的选择

| 情况 | 推荐方式 |
|---|---|
| 单个变量的加一、累加、位运算 | `atomic` |
| 一段固定位置的多行共享代码 | `critical` |
| 保护某个动态选择的数据对象，如 `msg_queues[dest]` | `omp_lock_t` |
| 每个队列、每个哈希桶、每个资源各自独立 | 每个对象一把锁 |

#### 6。不要混用不同机制保护同一份数据

危险例子：
```c
#pragma omp atomic
x += f(y);
```
同时另一处写：
```c
#pragma omp critical
x = g(x);
```
虽然两段代码都“有保护”，但它们不是同一把锁。`atomic` 不会自动等待 `critical`，`critical` 也不会自动等待 `atomic`。所以两个线程仍可能同时修改 `x`，结果不正确。

原则是：
> 同一个共享数据的同一类更新，应统一采用同一种同步方案。要么都用 `atomic`，要么都用同一个 `critical`，要么都用同一把锁。

#### 7。死锁：线程互相等待，谁也走不下去

1。“自己锁住自己”：
```c
#pragma omp critical
y = f(x);

double f(double x) {
    #pragma omp critical
    z = g(x);
}
```
外层已经进入了未命名的 `critical`，调用 `f()` 后又想进入同一个 `critical`。这会死锁。

2。两把锁的顺序不一致：
```text
线程 U：先获得锁 one，再等待锁 two
线程 V：先获得锁 two，再等待锁 one
线程 U 持有 one，等待 two
线程 V 持有 two，等待 one
```
两边都不肯释放已有的锁，程序永久卡住。避免方法是规定统一顺序，例如，所有线程都必须先获取锁 one，再获取锁 two。更好的设计是尽量避免同时持有多把锁。

最后还要注意：互斥不保证公平。某个线程可能反复抢到锁，另一个线程长时间抢不到，这叫“饥饿（starvation）”。因此临界区应尽量短，锁的使用也要尽量少。
